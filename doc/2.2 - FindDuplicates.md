# 2.2 Function: FindDuplicates (v0.7)

- Internal name: `FindDuplicates`
- Script: `System/Code/Database/FindDuplicates.ps1`
- Called by button: **Input initialisieren** (GUI label), after `InitializeFolder -Folder Input`, see `2 - FunctionOverview.md`
- Extends the base specification v0.20 (`1 - Base.md`). The base stays unchanged. Where this function would need a change to the base, it is listed in section 8.
- Language: this document and the code are in English. Only GUI-visible values are in German.
- Content taken over from the former combined specification (v0.8). Decisions confirmed there are marked "(confirmed)".

## 1. Purpose
- Checks every file in `Input` that has not been checked yet (`DuplicateChecked` empty) for an exact duplicate in `Result` or elsewhere in `Input`.
- Moves found duplicates to `Doublets` and places two shortcuts next to each one: one to the original file and one to the folder that contains it.
- Requires that `Input` (and `Result`) are initialized. It does not compute hashes itself.

## 2. Scope
- `InputAndResult` (confirmed): reads `Input` and `Result`.
- Moves files only from `Input` to `Doublets`. Never moves anything out of `Result` (confirmed).

## 3. Procedure
1. **Select:** all entries under `Input/` with `DuplicateChecked` empty, i.e. files newly recorded or recomputed by `InitializeFolder`. Earlier checked files are not checked again, so a rejected duplicate does not come back (confirmed).
2. **Check:** for each selected file, search the database for the same `Hash` (SHA-256) among all entries under `Input/` and `Result/`. Entries under `Doublets/` are ignored.
3. **Determine the original:**
   - If the hash exists in `Result`, the file in `Result` is the original and the file in `Input` is the duplicate.
   - If the hash exists only several times in `Input`, one file stays in `Input` as the original, all others are duplicates. The original is the file with the oldest capture date (`CaptureDate`, see `2.1 - InitializeFolder.md` section 4), i.e. the original date from EXIF and not the date a copy was made (confirmed). On a tie, the alphabetically first path.
4. **Plan:** for each duplicate: move the file to `Doublets` and create the two shortcuts right next to it.
5. **Preview** as in the base (Git-style, checkboxes). Left `Input` with red lines, right `Doublets` with green lines (file and both shortcuts). Duplicate and its shortcuts share one checkbox.
6. **Execute** the checked steps, write the log, update the database.
7. **Mark as checked:** every selected file gets `DuplicateChecked` = now, whether it was a duplicate, rejected, or unique.

## 4. Layout of `Doublets` (confirmed)
- All duplicates are placed directly in `Doublets`, without subfolders.
- The file keeps its name, e.g. `IMG_0412.jpg`.
- Right next to it are two Windows shortcuts (`.lnk`) (confirmed):
  - **File:** points directly to the original file. A double-click opens it.
  - **Folder:** points to the folder that contains the original. A double-click opens Explorer there.
- Shortcut names: file name including extension, then ` - `, then `Result` or `Input` (where the original is), then `File` or `Folder`:
  - `IMG_0412.jpg - Result File.lnk`
  - `IMG_0412.jpg - Result Folder.lnk`
- Explorer hides `.lnk` and shows `IMG_0412.jpg - Result File` and `IMG_0412.jpg - Result Folder`.
- Because the shortcut names start with the full file name, the file and its two shortcuts are always next to each other in alphabetical order.
- Name conflict (confirmed, underscore instead of date; renaming with `_2` stays allowed here, unlike `GroupByCaptureDate`): if a file with that name already exists in `Doublets`, the base rule applies. The file becomes `IMG_0412_2.jpg`, the shortcuts `IMG_0412_2.jpg - Result File.lnk` and `IMG_0412_2.jpg - Result Folder.lnk`.

```
SortingTool/
└─ Doublets/
   ├─ IMG_0412.jpg
   ├─ IMG_0412.jpg - Result File.lnk       → Result/Images/Holiday/IMG_0412.jpg
   ├─ IMG_0412.jpg - Result Folder.lnk     → Result/Images/Holiday/
   ├─ IMG_0412_2.jpg
   ├─ IMG_0412_2.jpg - Input File.lnk      → Input/Phone/IMG_0412.jpg
   ├─ IMG_0412_2.jpg - Input Folder.lnk    → Input/Phone/
   ├─ Invoice_2023.pdf
   ├─ Invoice_2023.pdf - Input File.lnk    → Input/Downloads/Invoice_2023.pdf
   └─ Invoice_2023.pdf - Input Folder.lnk  → Input/Downloads/
```

## 5. Rules
- Exact duplicates only (same SHA-256). Similar images (dHash) are not treated as duplicates for now (confirmed).
- Files with 0 bytes are never treated as duplicates, because all empty files have the same hash.
- A rejected duplicate (checkbox off) stays in `Input`, its database entry stays.
- No duplicate search within `Result`. `Result` is assumed to be free of duplicates (confirmed).
- Empty folders in `Input` caused by moving duplicates out are removed by the main program as in the base.

## 6. Database
- The entry of a duplicate stays and gets the new path, e.g. `Doublets/IMG_0412.jpg`.
- Entries under `Doublets/` are ignored by the check.
- Shortcuts get no entry.
- Shortcuts are never updated (confirmed). If an original is moved later, by the tool or by hand, its shortcuts point to nothing. That is accepted.

## 7. Log and undo
- File name: `YYYY-MM-DD_HH-MM-SS - Database - FindDuplicates.log`.
- New step type `LINK_CREATED` (shortcut created, with target), one line per shortcut.
- Summary: checked, duplicates found (original in Result / in Input), moved, rejected.
- Undo: the duplicate goes back to its old place in `Input`, the database path is reset. Both shortcuts next to it are removed (confirmed). This applies only to shortcuts the tool created itself and that are logged as `LINK_CREATED`. In the preview it appears as a red line with a checkbox, in the undo log as `LINK_REMOVED`.

## 8. Notes on the base (not entered there)
- **Fourth main folder `Doublets`** next to `Input`, `Result`, `System`. Base section 4 only has three.
- **Database paths** can also start with `Doublets/`.
- **New column `DuplicateChecked`** (see `2.1 - InitializeFolder.md`).
- **New file type `.lnk`:** the tool creates its own files for the first time, not only folders.
- **New step types** `LINK_CREATED` and `LINK_REMOVED`.
- **Further exception to "never delete":** on undo, the tool may remove shortcuts it created itself (confirmed). Base section 2 only lists empty folders.
