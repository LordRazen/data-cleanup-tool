# 2.1 Function: InitializeFolder (v0.13)

- Internal name: `InitializeFolder`
- Script: `System/Code/Database/InitializeFolder.ps1`
- Parameter: `-Folder Input` or `-Folder Result` (confirmed). The calling button passes the folder.
- Called by buttons (GUI labels): **Input initialisieren** (`-Folder Input`) and **Result initialisieren** (`-Folder Result`), see `2 - FunctionOverview.md`
- Extends the base specification v0.20 (`1 - Base.md`). The base stays unchanged. Where this function would need a change to the base, it is listed in section 7.
- Language: this document and the code are in English. Only GUI-visible values are in German.

## 1. Purpose
- One function for both folders (confirmed). Records every file in the given folder in the database with its hashes (`Hash` SHA-256, `SimilarityHash` dHash for images), as defined in base section 10.
- Also determines and stores the capture date of every file (`CaptureDate`, see section 4). `FindDuplicates` and `GroupByCaptureDate` use it.
- Only updates the database. Never moves, renames or creates files.
- Does not check for duplicates. That is the separate function `FindDuplicates` (see `2.2 - FindDuplicates.md`).

## 2. Scope
- Only the folder given by `-Folder` (confirmed): reads files in `Input` or in `Result`, writes the database. Never touches the other folder.
- The `scope` value therefore follows the argument: `Input` with `-Folder Input`, `Result` with `-Folder Result`. The value `Result` is new (see section 6).

## 3. Procedure
Exactly as base section 10 ("Initialisieren") for the given folder:
1. Entry with same path, same `Size` and `Modified`: unchanged, nothing computed.
2. Entry with same path, `Size` or `Modified` changed: hashes and capture date recomputed.
3. No entry: hashes and capture date computed. If an entry with the same hash exists whose file is missing at its old path, the path is updated (moved outside the tool). Otherwise a new entry is created.
4. Finally, entries under the given folder (`Input/` or `Result/`) whose file no longer exists are removed from the database (database row only, never a file).

Addition for the duplicate check:
- Every entry created or recomputed in steps 2 and 3 gets `DuplicateChecked` empty (see section 6). `FindDuplicates` only selects such entries under `Input/`, so for `Result` the mark has no effect.

## 4. Capture date
Goal: the date the photo (or video) was actually taken, not the date a copy was made. Windows resets `CreationTime` when a file is copied, so `CreationTime` alone is not reliable.

The capture date is taken from the first source that has a valid value:

| Order | Source | Applies to | Reliability |
|---|---|---|---|
| 1 | EXIF `DateTimeOriginal` (tag 0x9003) | JPEG, TIFF, most camera RAW, HEIC | time of capture, stays the same on copy |
| 2 | EXIF `DateTimeDigitized` (tag 0x9004) | same | usually identical to 1 |
| 3 | Windows property "Date taken" (`System.Photo.DateTaken`) or "Media created" (`System.Media.DateEncoded`) | HEIC, PNG, videos (MP4, MOV), if Windows can read them | time of capture, stays the same on copy |
| 4 | Date in the file name, e.g. `IMG_20240713_183012.jpg`, `PXL_20240713_…`, `IMG-20240713-WA0001.jpg` (WhatsApp), `Screenshot_2024-07-13-…` | all files | good, but only the day for some patterns |
| 5 | The older of `LastWriteTime` (modification date) and `CreationTime` | all files | weak. Windows keeps `LastWriteTime` on copy, but editing changes it |

- EXIF tag 0x0132 `DateTime` is **not** used, because image editors overwrite it when saving.
- Values before 1990 or in the future count as invalid (camera clock not set) and the next source is used.
- EXIF dates have no time zone. They are used as local time as stored.
- Technically: sources 1 and 2 with `System.Drawing` (built into PowerShell 5.1), source 3 with the Windows Shell (`Shell.Application`), nothing extra to install.
- Also read from EXIF and stored per file: GPS position as `Latitude` and `Longitude` (decimal degrees, GPS tags 0x0002 and 0x0004 with their N/S and E/W references), empty if there is none. Used by `2.6 - DeterminePlaceByGps.md`.
- Stored per file: `CaptureDate` (date and time) and `CaptureDateSource` (`ExifOriginal`, `ExifDigitized`, `WindowsProperty`, `FileName`, `FileSystem`).
- The same logic is a shared helper `Get-CaptureDate` in `Common.ps1`, so every function uses the same rules.

## 5. Preview
- No file changes, so no preview window. Progress bar and a summary at the end as in the base: new, unchanged, recomputed, detected as moved, missing.
- Can be cancelled at any time. Everything already computed stays stored.

## 6. Log
- File name as in the base, with the folder in the name: `YYYY-MM-DD_HH-MM-SS - Database - InitializeInput.log` or `... - InitializeResult.log`.
- Undo: nothing to undo, because no files are changed. The log is not offered in the undo list.

## 7. Notes on the base (not entered there)
- **One function instead of two:** base section 10 describes the two buttons as doing the same thing for different folders. Here this is one function with a parameter.
- **New column `DuplicateChecked`** in table `Files`: timestamp of the last duplicate check, empty = not yet checked.
- **New columns `CaptureDate` and `CaptureDateSource`** in table `Files` (see section 4).
- **New columns `Latitude` and `Longitude`** in table `Files` (see section 4).
- **New helper `Get-CaptureDate`** in `Common.ps1`.
- **New scope value `Result`:** base section 7 only knows `Input` and `InputAndResult`.
- **Function arguments:** base section 7 says every script gets the same inputs. Here a button additionally passes an argument (see `2 - FunctionOverview.md`).
